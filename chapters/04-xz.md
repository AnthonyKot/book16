# One character

The last chapter had no villain. This one has nothing else. Everything you are about to read was
done on purpose, by one person, patiently, over two and a half years, and `git` recorded all of it
under a name that a project full of careful people had learned to trust. The instructive part is
not that it happened. It is how ordinary each commit looks in isolation — how much the sabotage
resembles maintenance — and how little of the actual weapon is in the repository at all.

`git clone https://github.com/tukaani-project/xz`. This is the compression library that ships in
effectively every Linux distribution, maintained for years, essentially alone, by Lasse Collin.

## The welcome

In January 2022 a new contributor sends a patch. It is exactly the kind you want: defensive, small,
unglamorous.

```console
$ git log --all --author='jiat75' --reverse --format='%h %aI | committer=%cn | %s'
6468f7e4 2022-01-28T20:47:55+08:00 | committer=Lasse Collin | liblzma: Add NULL checks to LZMA and LZMA2 properties encoders.
```

Lasse applies it. [R1] Over the next six months "jiat75" sends more — test cleanups, coverage
scripts, CMake work — and in August 2022 Lasse writes the name into the file that says who this
project belongs to:

```console
$ git show 692de534fa -- AUTHORS
+    <lasse.collin@tukaani.org> and Jia Tan <jiat0218@gmail.com>.
```

One line. [R2] It is the nicest thing that can happen to a one-maintainer project: someone reliable
showed up and stayed. By the end of 2022 Jia Tan is pushing as a committer. By 2023 Jia is doing
more of the work than Lasse. Nobody in the room is watching a heist. They are watching a burnout
end. That is the point of the two and a half years — not the code, the *trust*. The backdoor could
not have been committed by a stranger. It had to be committed by the co-maintainer, and the way you
become the co-maintainer is to be genuinely helpful for a very long time.

## A name that only adds one thing

In June 2023 a second name appears, and this one is worth watching because it does exactly one
thing and then vanishes:

```console
$ git log --all --author='Hans Jansen' --format='%h %aI %cn %s'
```

Hans Jansen exists in this repository from June to October 2023. The work Hans contributes is
support for GNU indirect functions — ifunc, the mechanism that lets a library pick which version
of a function to use at load time, at runtime. It is a legitimate optimization. It is also the
exact hook the eventual payload needs: a place where a resolver runs early and gets to decide what
a symbol points to. Hans lands the ifunc groundwork and is never heard from again. [R3] I am not
going to tell you who Hans was; the git history cannot, and this book only tells you what the git
history can prove. What it proves is a name that appears, donates a loading mechanism, and
disappears — six months before that mechanism is used.

## The weapon that is not here

Now the famous part, and the first surprise is that you cannot `git show` it. The payload that made
CVE-2024-3094 — the code that hooks the SSH daemon's authentication — travelled in a file called
`build-to-host.m4`, a build script. If you go looking for it, you find nothing:

```console
$ git -C repos/xz log --all --oneline -- m4/build-to-host.m4  # (no output = never tracked)
```

Empty. The file was never committed. The only trace of it anywhere in this repository is its *name*,
added to a `.gitignore` nine days before the 5.6.0 release:

```console
$ git show 4323bc3e0c
    Update m4/.gitignore.
+build-to-host.m4
```

Read what that does. [R4, R5] The malicious build script gets generated into the release tarball by
the autotools machinery — but it is added to `.gitignore` so that if it ever appears in a working
tree, `git status` stays clean and no maintainer notices an unexpected file. The crime scene is the
*tarball*, the thing distributions actually download and compile. It is not the repository. Git, the
tool everyone trusts to show them what changed, was specifically taught to say nothing. The one-line
hygiene commit that taught it is so innocuous that after the breach Lasse himself cherry-picked it
forward, twice, because read in isolation it is exactly what it claims to be: tidying a `.gitignore`.

If you take one habit from this chapter, it is this: diff what you *ship* against what you *commit*.
They are not the same tree, and the gap is where this lived.

## The period

The second surprise is a single character, and it is the most audacious thing in the whole affair
because it is hiding in a commit whose message says it is a security *improvement*.

February 2024. Jia adds a build check for Linux Landlock — a kernel sandbox that would confine the
`xz` process, limiting what a compromised binary could do. Improving sandboxing is precisely what a
responsible maintainer does. Here is the check Jia added to the CMake build:

```console
$ git show 328c52da8a -- CMakeLists.txt
+        #include <sys/prctl.h>
+.
+        void my_sandbox(void)
```

Look at line two. A lone `.` on its own line, inside a C program that CMake compiles to test whether
Landlock is available. [R6] A single `.` is a syntax error. The test program never compiles, so the
check always fails, so CMake concludes Landlock is "not available," so `xz` never sandboxes itself —
which is exactly what you want if you are about to ship a backdoor and would prefer it not be caged.
The Autotools half of the same commit does not have the period. Only CMake. Someone sat in front of
that file and added one character.

It stayed until after the breach was public. When Lasse finally removes it, the entire fix is that
same character, deleted, and the message says out loud what the commit was:

```console
$ git show f9cf4c05ed
    CMake: Fix sabotaged Landlock sandbox check.
    It never enabled it.
```

```console
$ git show f9cf4c05ed -- CMakeLists.txt | grep -E '^[+-]'
-.
+
```

[R7] "Sabotaged." A minus, a dot, a plus, a blank line. The word did not exist in this tree until a
security researcher named Andres Freund, chasing a half-second of extra latency in SSH logins, found
the backdoor and went public on March 29. Everything before that date is written in the language of
maintenance. The sabotage and the fix are the same one character, pointing opposite directions.

## The exit

Jia's last commits are a tell you can only read backward. Three days before disclosure, at 1:50 in
the morning, Jia trims the project's `SECURITY.md`:

```console
$ git show -s --format='%h %aI %s' af071ef770
af071ef7 2024-03-26T01:50:02+08:00 Docs: Simplify SECURITY.md.
```

[R8] The lines removed are the ones that would have told a reporter to attach build logs and input
files — the exact artifacts that would have described the payload hidden in the test data. It is the
last commit Jia both authors and commits. Then the account goes dark.

The final word is Lasse's, returning to a house that turned out not to be his alone. His removal
commit reverts the backdoor and reads like an inventory of grief:

```console
$ git show e93e13c8b3
Remove the backdoor found in 5.6.0 and 5.6.1 (CVE-2024-3094).
...
  - The maintainer who added the backdoor has disappeared.
  - Backdoors are bad for security.
This reverts the following without making any other changes:
```

[R9] He lists the reverted commits like a table of contents for the attack, and then he edits
`AUTHORS` the way you edit a headstone: the second name comes out of the header and reappears lower
down, labelled, dated, sealed off. The years 2022 to 2024 become a marked interval. The project is
one person's again.

## At home

The uncomfortable lesson of xz is that none of the usual defenses were asleep. The code was reviewed.
The maintainer was diligent. The contributor was, by every visible signal, excellent — for years,
because being excellent for years was the attack. You cannot grep your way to catching this; the
malicious commits are, one at a time, indistinguishable from good ones, and the two that matter most
are a `.gitignore` tidy and a whitespace-shaped `.`.

But two habits would have narrowed it, and they cost nothing. First: your release tarball is not your
git tree — `git archive` a tag, diff it against what you actually publish, and look hard at anything
in the shipped artifact that is not in the repository, especially generated build scripts. Second:
read the *negative* path of every "improvement." A commit that adds a sandbox check is a commit that
can also quietly disable one, and the difference can be a single character that `git log --grep`
will never find because the message says the opposite of what the diff does. Blame, here, is not a
question of who to punish. It is a question of which line to read twice.
