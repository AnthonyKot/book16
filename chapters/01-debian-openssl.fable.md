# The nine minutes

Two commits, nine minutes apart, on a Tuesday afternoon in May 2006. Both by the same
person, both doing the responsible thing. Between them, `git` records the moment a maintainer
quieted a warning and, without knowing it, made every cryptographic key his distribution would
generate for the next two years guessable by anyone who cared to try.

I go looking for it in the Debian packaging repository, not upstream, because that is where it
lived. `git clone https://salsa.debian.org/debian/openssl.git`. Then I run the command I run on
any repo I'm about to trust:

```
$ git log --reverse --format='%h %aI %an %s' | head
90718ac527 1998-12-21T10:52:45+00:00 Ralf S. Engelschall This commit was generated by cvs2svn...
```

1998. Ralf Engelschall, upstream. That is a lie of a useful kind — the packaging history does
not start in 1998, it is *grafted onto* the upstream history, and the two lines share no common
ancestor. The command that tells the truth is `--first-parent`, which walks only the packaging
side: `3a6c894124`, 5 September 2005, Christoph Martin, `[svn-inject] Installing original source
of openssl`. **(R1, R2)** That is the real day one of the thing I'm reading — a `svn-inject`, an
overlay, seven years after the code it wraps. Keep that in your pocket: on a Debian repo,
`git log --reverse | head` shows you upstream; `--first-parent` shows you the packagers.

## The room

Here is what Kurt Roeckx knew on 2 May 2006, and here is what he did not.

He had a bug report, Debian #363516. Running the OpenSSL test suite under Valgrind and Purify —
memory checkers that flag any read of uninitialized memory — produced a wall of errors, all
pointing at one file, `md_rand.c`, the heart of OpenSSL's random number generator. The errors
were not in his code. They were in a design choice OpenSSL had made deliberately: to squeeze
every unpredictable scrap it could into the entropy pool, it hashed in a buffer *before* filling
it, uninitialized bytes and all. Garbage in, but garbage is entropy, and the whole point of a
random number generator is that more unpredictability is better.

The upstream authors knew this looked wrong. If you check out the 1998 SSLeay import and grep
the file, the tell is already there, eight years before Kurt touches it:

```
$ git grep -n -B1 -A1 'purify complains' d02b48c63a -- crypto/rand/md_rand.c
crypto/rand/md_rand.c-281-#ifndef PURIFY
crypto/rand/md_rand.c:282:		MD_Update(&m,buf,j); /* purify complains */
crypto/rand/md_rand.c-283-#endif
```

**(R3)** One spot, and one spot only, is wrapped in `#ifndef PURIFY` — a switch you flip when
you're running the memory checker, so the deliberately-dirty read disappears and Purify stops
complaining. That comment, `/* purify complains */`, is a scope. It says: *this specific read,
of this throwaway output buffer, is the one Purify hates, and here is the one place we make an
exception.* It does not say the practice is wrong. It says one function is noisy under one tool.

Kurt read that comment as a rule. On 2 May at 16:25 he imports upstream's `md_rand.c` into the
package. Nine minutes later, at 16:34, he generalizes the exception.

## The turn

```
$ git show --format=fuller --stat 8f27a7dc02
    Don't add uninitialised data to the random number generator.  This stop
    valgrind from giving error messages in unrelated code.  (Closes: #363516)
 debian/changelog | 3 +++
 rand/md_rand.c   | 6 ++++++
```

**(R5)** Six lines. Read the diff and you can watch the reasoning happen:

```
@@ static void ssleay_rand_add(...)
+/*
+ * Don't add uninitialised data.
 		MD_Update(&m,buf,j);
+*/
...
@@ static int ssleay_rand_bytes(...)
 #ifndef PURIFY
+/*
+ * Don't add uninitialised data.
 		MD_Update(&m,buf,j); /* purify complains */
+*/
 #endif
```

Two functions, two identical comments, two `MD_Update` calls commented out. The second one is
the one Purify actually complained about — the throwaway buffer, already behind `#ifndef PURIFY`.
Fine. But the first one is in `ssleay_rand_add`, and `ssleay_rand_add` is not a throwaway. It is
*the function that mixes the caller's seed into the pool.* Every call that says "here is some
entropy — the process ID, the time, the contents of `/dev/urandom`" arrives through
`ssleay_rand_add` and gets hashed in by exactly the `MD_Update(&m,buf,j)` he just wrapped in
`/* */`.

He has not disabled a Purify workaround. He has disabled the seeding. From now on the only thing
feeding the pool is a few bytes of process ID — and a PID on Linux is a number under 32,768. The
space of keys the generator can produce collapses from astronomical to something you could
enumerate over a weekend.

Nobody in the room knows this. The commit closes a bug. The changelog stanza he drops it into is
even dated four weeks *earlier* than the commit — `Thu, 6 Apr 2006` **(R6)** — because it lands
in an unreleased entry that was already open. It reads like housekeeping. <!-- CHECK: characterization that Kurt believed this was a benign valgrind fix — supported by the commit message and by the later public account, but "belief" is inference; keep as narration, not asserted fact -->

## Four months in the wrong place

And then the best part, the part that is pure `git` and that no CVE writeup will tell you: for
four months, it doesn't matter. Because he put the file in the wrong place.

Look at where `md_rand.c` landed on 2 May: `rand/md_rand.c`. **(R4)** But OpenSSL 0.9.8 compiles
`crypto/rand/md_rand.c`. Debian's packaging of this era stored *overlays* — only the upstream
files the maintainer meant to modify, laid over an unpacked tarball at build time. A modified
file at a path the build doesn't use is a no-op. You can prove it at the release tag:

```
$ git ls-tree --name-only debian/openssl-0.9.8b-1 rand/md_rand.c crypto/rand/md_rand.c
rand/md_rand.c
```

**(R7)** The sabotaged file exists only at the dead path. `crypto/rand/md_rand.c` isn't there;
the build used the pristine upstream one. Version 0.9.8b-1 *claims* the valgrind fix in its
changelog and ships a perfectly good random number generator. The bug is checked in and inert.

Valgrind, of course, is still noisy — because the fix isn't really applied. So on Sunday
17 September, at 13:32, Kurt fixes that:

```
$ git show --format=fuller --stat 33a9d075e9
    Move the modified rand/md_rand.c file to the right place really fixing #363516.
 {rand => crypto/rand}/md_rand.c | 0
```

**(R8)** "Really fixing." A pure rename, zero content change, moving the file onto the path the
compiler reads. *That* is the commit that arms it — six months of released Debian and Ubuntu
will descend from this Sunday afternoon, not from May. And fifty-seven minutes later, the
compiler gets its one and only chance to object, and is overruled:

```
$ git show --format=fuller a590e4f469
    Make md_rand.c build, nested comments don't work.
...
 #ifndef PURIFY
-/*
- * Don't add uninitialised data.
+#if 0 /* Don't add uninitialised data. */
 		MD_Update(&m,buf,j); /* purify complains */
-*/
+#endif
```

**(R9)** The `/* */` wrapper he'd put around the *second* call sat inside a line that already
had a `/* purify complains */` comment — a comment inside a comment, which C won't compile. So
he converts that one to `#if 0`. Notice what the compiler caught and what it didn't: it choked on
the harmless half, the throwaway buffer, because that line happened to contain an inner comment.
The fatal half — the seed path in `ssleay_rand_add` — had no inner comment, compiled clean the
first time, and drew no protest at all. The build break was the last automated check between
Kurt and the disaster, and it was looking at the wrong function.

## The blast radius

The keys generated by that build were predictable for twenty months. Every SSH host key, every
SSL certificate, every OpenVPN key made by a Debian or Ubuntu machine between September 2006 and
May 2008 came from a pool with at most fifteen bits of entropy. You did not break the key. You
enumerated it — precompute every possible key, look yours up. <!-- CHECK: "at most 15 bits / PID-only entropy" and the 32,768 figure — standard in the public analysis of CVE-2008-0166; source in review pass -->

The fix, when it comes on 7 May 2008, is one sentence:

```
$ git show --format=fuller --stat f7949d6e0a
    ssleay_rand_add() really needs to call MD_Update() for buf.
 crypto/rand/md_rand.c       | 3 ---
 debian/changelog            | 8 ++++++--
 debian/libssl0.9.8.postinst | 2 +-
```

**(R10)** Three lines removed from `md_rand.c` — the `/* */` around the seed call, deleted, so
`MD_Update(&m,buf,j)` runs again. That's the whole repair. The subject names the function and
the mechanism precisely: `ssleay_rand_add() really needs to call MD_Update() for buf`. It is
the confession of a man who now understands exactly which line he commented out. What it does
*not* say is any of the words a user would search for. It does not say "security." It does not
say "regenerate your keys." It does not name the CVE.

That's not a guess. Grep the entire repository:

```
$ git log --all --grep=CVE-2008-0166 --oneline
$ git log --all --grep=DSA-1571 --oneline
```

**(R11)** Nothing. Two empty results. The most catastrophic bug in Debian's history is invisible
to the search anyone would actually type. If you want to find it in `git`, you cannot grep the
message; you have to grep the *mechanism* — `git log -S 'uninitialised' -- '**/md_rand.c'` — and
read the diffs.

And it went out the door wearing someone else's clothes. Three hours before Kurt's fix, Christoph
Martin had prepared version 0.9.8g-9 as a routine translations update **(R15)**. Kurt reused that
same version stanza: the changelog for the security release lists `[ Christoph Martin ]` updated
debconf translations, then `[ Kurt Roeckx ]` and one line about `MD_Update` **(R10)**. The
urgency flips from `low` to `high` and the `postinst` restart threshold moves so upgrading
services get prompted — the only two signs, in the packaging, that this was the fire and not a
Tuesday.

## The reconstruction

One more thing, because it changes how you read a tag. The parallel fix for the *stable* release,
`etch`, is in this repo as tag `debian/openssl-0.9.8c-4etch3`. Its changelog stanza is signed by
the security team and dated May 2008. But look when the commit was actually made:

```
$ git log -1 --format=fuller debian/openssl-0.9.8c-4etch3
AuthorDate: Sat May 16 14:56:28 2009 +0000
    Re-introducing seeding of the random number generator.
```

**(R12)** 2009. A year late. The archive shipped `4etch3` to users in May 2008; the *version
control* only got it backfilled a year afterward, in one sitting, with the 2008 changelog text
preserved inside a 2009 commit. And you can prove the branch was hollow in between — the unstable
fix is not even an ancestor of the etch line:

```
$ git merge-base --is-ancestor f7949d6e0a origin/debian/etch; echo exit=$?
exit=1
```

**(R13)** Exit 1: not an ancestor. Anyone reading `origin/debian/etch` in this repository sees
the commented-out seed sitting there from April 2008 until a Saturday in May 2009. A tag named
like a shipped version is not a receipt that the version control ever held that code when it
shipped. Compare the tag's author date to its changelog trailer; if they disagree by a year,
you're looking at a reconstruction.

The last word belongs to the leftover. In July 2009 Debian finally split its in-tree edits into
named quilt patches — and the *other* half, the genuinely-harmless throwaway-buffer wrapper, got
checked in with a name of its own: `debian/patches/valgrind.patch` **(R14)**. It carried the
name of the original excuse forward through 1.0.0, 1.0.1, 1.0.2, rebased release after release
until 2016, when upstream deleted `md_rand.c` and it finally had nowhere to live. The lesson
Debian took from the worst key disaster of the decade was "use quilt," and they named the
survivor after the thing that started it.

## At home

The dig here isn't the CVE; it's the shape of it, and the shape recurs. A `#ifndef SANITIZER`
that disables a *read* is a loaded gun, because the next person to touch the file will read the
comment as a rule and widen it. So: `git log -S` on any comment that mentions a tool — `valgrind`,
`purify`, `asan`, `coverity`. Find every place someone quieted a checker, and check whether the
next commit quieted it somewhere the checker was right. And when you go hunting for the worst
thing that ever happened to a codebase, don't grep the commit messages. The people who did it
were closing a bug. They wrote down the ticket number, not the crime.
