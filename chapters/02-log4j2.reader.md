# To improve performance

In December 2021 the internet caught fire. A flaw in a small, unglamorous piece of software called
Log4j — a tool that does nothing more exciting than write messages to a log file — turned out to
let an attacker take over almost any server that used it, and Log4j was used by almost everything.
For about a week, every security team on earth was awake at once.

When something that bad happens, we reach for a villain. Someone was lazy. Someone cut a corner.
Someone should have known.

Here is the uncomfortable thing the record shows: nobody did any of that. There is no villain in
this story. There are five ordinary, sensible decisions, made by competent people across eleven
years, each one of which you would have approved without a second thought — and which, only when
you stack all five on top of each other, add up to a catastrophe. Nobody could see the whole thing,
because at no single moment did the whole thing exist. It was assembled the way a coral reef is:
one small, reasonable deposit at a time.

Let me walk you up the reef.

## 2010 — a helpful little feature

The first deposit is a convenience, and a nice one. The maintainer adds a feature that lets you put
placeholders in your log settings — you write something like `${username}` and the software fills
in the real value when it runs. Every logging tool has this. It saves people typing.

But look closely at what it quietly establishes. A piece of text with `${...}` in it is no longer
just *text* the program prints. It is now an *instruction* the program follows. And the list of
instructions it will obey is left open on purpose — so that later, anyone can teach it a new trick
just by plugging one in. In 2010 the tricks are harmless (insert a username, insert a date) and the
text always comes from the person running the software, who is trusted.

That last part is the whole safety argument, and it is about to spring a very slow leak.

## 2012 — to improve performance

Now the deposit that matters, and it is the least suspicious one in the entire story. That is
exactly why it's worth slowing down for.

Two years on, someone notices the placeholder-filling is happening in a slightly wasteful spot, and
moves it somewhere more efficient. The commit message says, plainly, "to improve performance." It
is a good change. Anyone reviewing it would wave it through; *making the same work happen faster* is
the most approvable thing a programmer can do.

Except — and no one felt this at the time — the *new* spot means the placeholder-filling now runs
over the actual log messages. Not the settings the trusted operator wrote. The messages. Which are
full of whatever the outside world sent: the username someone typed into a login box, the browser
details a visitor's computer announced, the text of a search. If any of that outside text happens to
contain `${...}`, the software now treats it as an instruction and obeys it.

~ A change made purely for speed had quietly connected the outside world to the instruction-follower.

The programmer optimized a layout. He also, without anyone noticing, pointed a loaded feature at the
entire internet. The single most transferable lesson in this whole book lives in that gap: *a change
that only speeds things up can still change what the code is capable of.*

## 2013 — one more trick, with a convenient exception

Ten months later, someone adds a genuinely useful new instruction: the ability to look up a value
from the company's central directory — a normal thing big enterprise systems do. It gets plugged in
next to the harmless ones, exactly as designed.

There is one small courtesy built into it. Normally it only looks things up inside the company's own
safe directory. But — to be helpful — if you write your request in a certain fuller form, it will go
fetch from wherever you point it instead. The convenience that lets an employee point it at an
internal resource is the same convenience that lets a stranger point it at *their own server,
anywhere in the world.*

Now every piece is on the table, and no single person set them there. Outside text reaches the
instruction-follower (2010, then 2012). One of the instructions can fetch from a remote address
(2013). So a log line containing the right little string — the kind of thing an attacker can get a
website to log just by typing it into a form — becomes a command that reaches out to the attacker's
computer and runs whatever it sends back. That door has been standing open since a Thursday
afternoon in 2013, and it will stay open for eight years while everyone walks past it.

## 2016 — they saw it, and did not see it

This is the part that aches.

In 2016, some users complained. Their `${...}`-shaped text was being eaten — the software was
treating their data as instructions and mangling it. That complaint *is* the vulnerability,
described from the inside as a minor annoyance about two programs not getting along.

The maintainers responded, correctly and conscientiously, to the problem as reported. They added an
off switch — a way to tell the software "stop treating messages as instructions." Good. But they
left it switched *off by default*, because from where they sat there was no reason to alarm
everyone; it was a niche compatibility fix.

So the exact protection that the entire internet would frantically scramble to turn on in December
2021 had been sitting inside the software, one switch away, since 2016. Almost nobody flipped it,
because from the inside there was nothing visible to flip it *for*. The users had reported the
danger. It just didn't look like danger. It looked like a bug about text.

~ An off switch whose default is off is not a protection. It is a comment.

## The fire, and the name in the test

By the time the world found out, in December 2021, the door had been open for eight years. What
happened next is the only part most people remember, so here is the one detail that isn't in the
write-ups.

On the first Saturday night of the emergency, the maintainers rushed out a patch to start closing
the hole — and in the same commit, they added a test with a very on-the-nose name: a small mock
"exploit," checked into the code, whose only job was to *fail* if the dangerous behavior ever ran
again. They named it, in plain letters, `JndiExploit`. They were, at that exact moment, still not
sure they had actually contained it — and they were right to worry; it took two more emergency
releases over the following week to fully shut the door. You can watch the fear in the file names.

## What to carry away

The lesson of the worst software vulnerability in recent memory is not "don't be careless." Every
person in this story was careful. The lesson is stranger and more useful: a system grows a
catastrophe the same way it grows a feature — a little at a time, by people who each saw only their
own small, sensible piece. The trap is never in one commit. It is in the *sum*, and no one is ever
standing where they can see the sum.

So if you build things: the dangerous change is almost never the one that looks dangerous. It's the
one labelled *convenience*, or *speed*, or *cleanup* — the one that quietly connects two safe things
into one unsafe thing. When you move where the outside world's input can reach, stop and look, even
if all you did was make something faster. And if you ever build a system that can be taught new
tricks on the fly, write down — today, before anything goes wrong — the list of tricks it must never,
ever be allowed to learn.
